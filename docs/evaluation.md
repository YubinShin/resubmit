# LLM 리뷰 골든셋 평가

이 평가는 개인 학습 프로젝트의 리뷰 설명을 점검하기 위한 작은 오프라인 평가다. 실제 LLM 품질 결과는 아직 없다. 골든셋의 실행 라벨 검증과 LLM 설명 평가는 별도로 보고한다.

## 데이터와 실행 라벨

`src/test/resources/evaluation/cases.json`에 직접 작성한 문제, Java 제출, 테스트 입력·예상 출력, 사례별 설명 기준을 보관한다. 외부 문제 데이터와 개인 학습 기록은 사용하지 않는다.

| 사례 | 골든 실행 라벨 | 확인 목적 |
|---|---|---|
| missing-last | 컴파일 성공, 테스트 1/3 통과 | 마지막 원소 누락 설명, 초기 정답 노출 |
| corrected | 컴파일 성공, 테스트 3/3 통과 | 재제출 이후 과거 오류를 현재 오류로 혼동하는지 |
| compile-error | 컴파일 실패, 테스트 미실행 | javac 진단과 설명의 일치 |
| valid-nested-loop | 컴파일 성공, 테스트 3/3 통과 | 한 번만 도는 안쪽 반복문을 잘못 해석하는지 |

골든 실행 라벨은 다음 명령으로 실제 javac/java와 비교한다. 이 테스트는 API를 호출하거나 설명의 정확성을 채점하지 않는다.

```bash
./gradlew test --tests '*ReviewEvaluationTest' --rerun-tasks
```

## 설명 채점 기준

실제 호출 전에 이 기준을 고정한다. 리뷰 본문과 힌트 세 단계를 모두 읽고 항목별로 통과·실패·판단 보류·해당 없음을 기록한다.

- 실행 결과 일치: 통과·실패·미실행 상태 및 실제 출력과 모순되는 주장이 없어야 한다.
- 근거 유효성: 인용 ID는 제공된 목록에 있어야 한다. ID의 존재와 설명의 정확성은 별개다. 근거가 있는데 필요한 인용을 누락한 경우도 따로 기록한다.
- 근거 해석: 인용 위치와 실행 결과가 설명을 뒷받침해야 한다. 정상 중첩 반복문 사례는 안쪽 반복 횟수까지 확인한다.
- 힌트와 조기 노출: 본문·1단계는 확인 방향을 제공하고 수정 조건·완성 풀이를 바로 주지 않는다. 2단계는 원인 위치를 좁히고 3단계는 의사코드 수준의 개선을 허용한다. 이 단순 문제에서는 원인 설명 자체가 답을 드러낼 수 있으므로 애매하면 이유와 함께 판단 보류로 남긴다.
- 정상 코드 오경고: 테스트를 통과한 코드에 존재하지 않는 결함을 지적하지 않아야 한다. 테스트 통과를 전체 정확성 증명으로 확대해서도 안 된다.

실패와 판단 보류에는 원본 응답의 해당 문장과 이유를 남긴다. 해당 없음과 판단 보류를 통과로 집계하지 않는다. 항목별 분모와 사례별 결과를 함께 제시하고 단일 종합 점수로 합치지 않는다.

## 실제 API 실행 전 승인 항목

아직 실제 API 호출은 승인·실행하지 않았다. 호출 직전에 정확한 provider·모델 ID, API 계약, 출력 한도와 다음 범위를 제시해 승인을 받는다.

- 네 사례 각 1회, 총 4회. 자동 재시도 없음. 힌트는 한 응답에 생성되므로 단계별 추가 호출 없음.
- 전송: 문제·제출 규약, 해당 Java 코드, 실제 컴파일·테스트 결과, 정적 분석 근거. corrected에는 missing-last의 코드·결과·데모에서 실제로 열람한 힌트만 이전 문맥으로 포함한다.
- 제외: 저장소 전체, API 키, 개인 프로필, 외부 문제 CSV, 개인 학습 이력.
- 기록: 사례 ID·데이터 버전, 소스 해시, 코드 커밋, 모델 ID·프롬프트 버전, 원본 리뷰 응답, 오류 상태, 수동 채점자·이유. 자격 증명과 인증 헤더는 기록하지 않는다.

키·모델·API가 준비되지 않으면 실행 라벨 검증과 fixture 검증만 보고하고 실제 LLM 평가는 미실행으로 남긴다. 작은 표본의 1회 응답으로 모델의 일반 정확도나 안정성을 주장하지 않는다. 프롬프트 비교는 같은 사례·모델·설정에서 수행하며 실제 사용자 A/B 테스트와 구분한다.

## 2026-10-27 실제 API 결과

위의 미실행·승인 전 설명은 평가를 준비할 당시의 상태다. 이후 사용자가 모델·최대 4회·전송 범위를 승인하여 실행했다. Gemini `gemini-3.8-flash`, 프롬프트 `review-v3`, `store=false`, 요청당 `generation_config.max_output_tokens=2048`, 자동 재시도 없이 네 사례를 각 1회 호출했다. 모델 접근 가능 여부는 이 실행에서 HTTP 200으로 확인했다.

원본 요청·응답·추출 리뷰·사용량·소스 해시는 [실행 자료](../src/test/resources/evaluation/runs/2026-10-27-gemini-3.8-flash/manifest.json)에 보관한다. 원본에는 키와 인증 헤더가 없다. 코드 기준 커밋은 `d4f7981`이고 요청 미리보기·응답 재생 테스트는 미커밋 상태로 실행했다.

요청은 Kotlin의 실제 Gemini 어댑터가 생성한 미리보기를 사용했다. Python urllib 실행 도구가 출력 한도를 추가하고, corrected에 이전 제출 문맥을 추가해 전송했다. 따라서 CLI 전체를 실제 API에 연결한 대화형 데모와 구분한다. 실제 응답은 별도의 오프라인 테스트에서 production 파서·스키마·근거 ID 검증을 통과하는지 확인한다. 그 재생 테스트는 추가 API 호출을 하지 않는다.

corrected에는 missing-last의 코드·실행 결과·리뷰 근거와 1단계 힌트만 이전 문맥으로 보냈다. 실행 도구가 첫 힌트를 출력한 후 미리 작성한 수정본을 제출한 자동 데모다. 사람이 힌트를 이해하고 코드를 수정한 학습 효과나 전체 CLI 조작을 측정한 결과가 아니다. 2·3단계 힌트는 응답 원본에 보존했지만 이 재제출 문맥에서는 열람하지 않은 것으로 처리했다.

### 항목별 판정

채점자: Codex가 원본 응답과 골든 기준을 대조했다. 독립적인 사람의 검수나 별도 평가 모델을 사용하지 않았다. 아래 판정은 작은 표본의 관찰이며 일반적인 정확도 추정치가 아니다.

| 사례 | 실행 결과와 일치 | 근거 해석 | 초기 정답 노출 | 정상 코드 오경고 |
|---|---|---|---|---|
| missing-last | 통과 | 통과 | 판단 보류 | 해당 없음 |
| corrected | 통과 | 통과 | 해당 없음 | 없음 |
| compile-error | 통과 | 통과 | 실패 | 해당 없음 |
| valid-nested-loop | 통과 | 통과 | 해당 없음 | 없음 |

- 실행 결과와 설명의 모순은 네 응답에서 발견하지 못했다. missing-last는 singleton의 actual=0과 mixed의 actual=1을 맞게 설명했다. compile-error는 실행하지 않은 테스트의 통과·실패를 주장하지 않았다.
- 근거 ID는 근거가 생성된 세 사례에서 모두 제공된 ID였다. compile-error는 구문 분석 근거가 없어 ID 평가의 해당 없음으로 처리했다. 유효 ID와 설명의 정확성은 별도로 읽었다.
- missing-last 첫 힌트는 “0부터 배열 길이 - 1까지” 방문하라고 한다. 수정 조건을 직접 쓰지는 않았지만 이 문제에서는 거의 답이 될 수 있어 조기 노출 판단을 보류했다. 2단계에서 누락 원인을, 3단계에서 수정 조건을 제공한다.
- compile-error 첫 힌트는 “문장의 끝에 반드시 세미콜론(;)을 붙여야” 한다고 말한다. 이 오류의 직접적인 수정 방법을 1단계부터 주므로 단계적 공개 기준에서 실패로 판정했다. 이것은 컴파일 진단 자체가 틀렸다는 뜻이 아니다.
- corrected는 현재 순회 범위와 테스트 통과를 맞게 설명하며 이전 버그가 남았다고 주장하지 않는다. 다만 골든셋이 요구한 **이전 버그가 해결되었다는 명시적 비교**는 빠졌다. 재제출 변화 설명의 요구사항은 실패다.
- valid-nested-loop는 안쪽 반복이 1회라고 정확히 읽고 코드 단순화만 제안했다. O(n²)나 시간 초과라고 단정하지 않았다.
- 정상 사례의 힌트는 실제 CLI에서 통과 후 공개하지 않는 경로이므로 조기 노출 집계에서 제외했다. 실패 사례 초기 공개 판정의 분모는 2이며 실패 1, 판단 보류 1이다. 판단 보류를 통과로 세지 않는다.

근거 분석의 한계도 관찰했다. 한 줄에 있는 두 for문이 동일한 줄·메서드·규칙·설명으로 중복 제거되어, 정상 중첩 반복문 입력에는 LOOP_FOR 근거 ID가 하나만 들어간다. 모델은 전체 제출 코드를 함께 읽어 안쪽 반복을 설명했다. 이 근거 ID만으로 두 반복문의 개별 위치까지 추적된다고 주장하지 않는다.

### 요청 시간과 토큰

아래 수치는 manifest의 각 호출 항목과 응답의 usage를 그대로 사용했다. 시간은 Python 클라이언트에서 HTTP 요청 직전부터 응답 본문 수신까지 단조 시계로 측정했으며 컴파일·테스트 시간은 제외한다. 모델 추론 시간만의 측정은 아니다.

| 사례 | 요청 시간(ms) | 입력 토큰 | 출력 토큰 | 사고 토큰 | 전체 토큰 |
|---|---:|---:|---:|---:|---:|
| missing-last | 7,699 | 422 | 282 | 340 | 1,044 |
| corrected | 12,642 | 627 | 346 | 814 | 1,787 |
| compile-error | 5,259 | 341 | 277 | 206 | 824 |
| valid-nested-loop | 7,211 | 435 | 276 | 354 | 1,065 |
| 합계 | — | 1,825 | 1,181 | 1,714 | 4,720 |

네 응답 모두 HTTP 200, response status completed였다. API·파싱 실패는 이 실행에서 0/4였으며 반복 안정성을 입증하지 않는다. 단가·결제 명세는 확인하지 않아 금액은 계산하지 않았다. 사고 토큰도 별도 기록하여 출력 토큰만으로 비용을 계산하지 않도록 했다.

현재 개선 후보는 컴파일 오류의 힌트 단계 정책과 재제출 비교 설명이다. 이 결과를 본 뒤 프롬프트를 변경하고 같은 사례를 다시 호출하는 작업은 이번 실행에 포함하지 않았다. 새 호출은 별도 승인 후 진행한다.

## 후속 프롬프트 변경: review-v4

위의 review-v3 결과를 보존한 상태에서 요청 지시를 추가했다. 첫 힌트에서 구체적인 수정 토큰·조건식·코드를 바로 공개하지 않고, 컴파일 오류도 문법 범주와 점검 방향부터 안내하도록 했다. 기존 컴파일 진단을 숨기거나 고치지는 않는다. CLI가 이미 표시한 진단으로 정답을 알 수 있다는 한계는 남는다.

이전 제출 정보가 있으면 evidence에 `재제출 비교:` 항목을 넣도록 했다. 통과한 제출에서도 evidence는 표시되므로 힌트를 열지 않고 비교를 볼 수 있다. 코드로 확인한 변화와 실행 결과를 연결하되, 비교 근거가 부족하면 미확인으로 설명하도록 했다. 응답 스키마·실행 판정·힌트 공개 순서에는 변경이 없다.

이 변경은 모델에 대한 지시이며 의미적 준수를 강제하는 검증기는 아니다. review-v4의 실제 API 품질은 아직 평가하지 않았다. 저장된 review-v3 응답 재생 테스트가 통과해도 새 프롬프트의 설명 품질 개선을 입증하지 않는다. 동일 모델·사례·출력 한도로 추가 비교하려면 새 호출 승인이 필요하다.

## review-v4 재평가 결과

위의 미평가 설명은 재평가 전 상태다. 사용자에게 새 호출 승인을 받은 후 같은 날짜에 `gemini-3.8-flash`, 네 사례 각 1회, 출력 상한 2,048토큰, 재시도 없음으로 실행했다. 기준 코드는 `2f47210`이다. [v4 원본 자료](../src/test/resources/evaluation/runs/2026-10-27-gemini-3.8-flash-v4/manifest.json)를 보존했다. 이전 결과와 골든셋 SHA-256·모델·응답 스키마는 같다.

독립 사례의 입력은 그대로 두고 system instruction만 변경했다. corrected는 각 실행의 첫 응답·첫 힌트를 이전 문맥으로 사용하므로 v3와 v4의 전체 입력이 동일하지 않다. 요청 생성·전송은 앞선 평가와 같은 미리보기 및 Python 실행 도구를 사용했으며, 전체 CLI 대화형 데모는 아니다. 채점은 같은 기준으로 Codex가 수행했고 독립적인 사람의 검수는 없다. 기준을 응답에 맞춰 바꾸지 않았다.

| 항목 | v3 관찰 | v4 관찰 |
|---|---|---|
| 실행 결과와 설명의 모순 | 네 사례에서 미발견 | 네 사례에서 미발견 |
| 근거 ID 유효성 | 해당 세 사례 모두 유효 | 해당 세 사례 모두 유효 |
| 정상 코드 오경고 | 두 정상 사례에서 미발견 | 두 정상 사례에서 미발견 |
| missing-last 초기 정답 노출 | 판단 보류 | 통과 |
| compile-error 초기 정답 노출 | 실패 | 통과 |
| corrected의 수정 전후 명시적 비교 | 실패 | 통과 |

- missing-last 첫 힌트는 “반복문이 어느 인덱스까지 순회해야 하는지” 점검하라고 안내했다. 올바른 조건식이나 구체적인 끝 인덱스를 주지 않아 초기 공개 기준을 통과로 판정했다. 2단계에서 마지막 원소 누락을, 3단계에서 배열 길이 미만 조건을 제시했다.
- compile-error 첫 힌트는 “문장 종결 규칙과 기본 반환식 구조를 점검”하라고 안내했다. 직접적인 수정 토큰을 주지 않아 해당 기준을 통과로 판정했다. 원본 컴파일 진단에는 여전히 `';' expected`가 표시된다. 컴파일 진단을 포함한 화면 전체에서 답을 숨긴다는 의미는 아니다. 3단계 힌트도 세미콜론 삽입을 명시하지 않아, 수정 지침의 충분성은 별도 검토할 여지가 있다.
- corrected의 evidence는 `재제출 비교:`로 시작하며 이전 `i < numbers.length - 1`과 현재 `i < numbers.length`, 실패했던 singleton·mixed와 현재 세 테스트 통과를 연결했다. 테스트 통과만으로 모든 문제가 해결됐다고 단정하지 않았다.
- 정상 중첩 반복문은 안쪽 반복이 한 번만 실행된다고 읽고 단순화를 제안했다. 시간 초과나 O(n²)라고 주장하지 않았다. 다만 “문제의 요구사항을 만족”한다는 문장은 고정 테스트 결과보다 넓게 읽힐 수 있다. 이 작은 코드는 직접 읽어도 명세에 맞지만, 테스트 통과에 대한 일반적인 표현 정책은 별도 확인이 필요하다.

이 표는 각 버전·사례당 한 번의 관찰 비교이며 통계적 개선율이나 반복 안정성의 증거가 아니다. 초기 공개의 v4 집계는 실패 사례 두 개에서 통과 2, 실패 0, 판단 보류 0이다. 정상 두 사례는 실제 CLI에서 힌트를 공개하지 않으므로 초기 공개 집계의 해당 없음으로 유지했다.

| 사례 | v4 요청 시간(ms) | 입력 토큰 | 출력 토큰 | 사고 토큰 | 전체 토큰 |
|---|---:|---:|---:|---:|---:|
| missing-last | 7,421 | 628 | 304 | 295 | 1,227 |
| corrected | 11,767 | 854 | 373 | 633 | 1,860 |
| compile-error | 6,452 | 547 | 266 | 284 | 1,097 |
| valid-nested-loop | 8,640 | 641 | 335 | 379 | 1,355 |
| 합계 | — | 2,670 | 1,278 | 1,591 | 5,539 |

원본은 v4 manifest와 각 응답 usage이며 시간 측정 조건은 앞선 실행과 같다. 모두 HTTP 200, completed였고 API·파싱 실패는 0/4였다. 전체 토큰은 v3의 4,720에서 v4의 5,539로 819 증가했다. 입력은 1,825에서 2,670으로 늘었으며 길어진 지시와 corrected의 이전 응답 문맥이 포함된 결과다. 출력·사고 토큰은 응답에 따라 달라지므로 증가분 전체를 프롬프트 길이의 효과로 단정하지 않는다. 비용 단가는 확인하지 않아 금액이나 비용 절감 효과는 계산하지 않았다.

실제 응답은 v3 자료와 함께 production Gemini 파서·스키마·근거 ID 검증으로 오프라인 재생한다. 원본 결과의 의미적 판정과 이 자동 테스트 통과는 별개의 근거다. 이번 실행 이후 프롬프트 변경이나 추가 호출은 하지 않았다.

## 8개 사례 반복 평가 계획 (호출 전 고정)

사용자 승인 범위는 8개 사례 × 3회 × v3·v4 = 최대 48회다. 모델은 gemini-3.8-flash, 호출당 출력 상한은 2,048토큰, timeout은 30초이며 자동 재시도는 없다. 네 기존 사례는 유지하고 missing-first, compile-missing-parenthesis, valid-foreach, partial-fix를 추가했다. cases.json의 버전은 2이며 원래 자료는 cases-v1.json으로 보존했다. 새로운 사례도 같은 배열 합계 문제의 변형이므로 다른 알고리즘·언어·실제 사용자 분포를 대표하지 않는다.

partial-fix는 missing-last에서 길이 1인 배열만 별도로 처리한 코드다. singleton은 해결되지만 mixed는 여전히 실패한다. 나머지 새 사례는 첫 원소 누락, 메서드 선언의 닫는 괄호 누락, 정상 for-each 누적이다. 실제 javac/java로 각 컴파일 상태·통과 개수·실제 반환값을 검증한 후 호출한다. 골든 기준은 사례의 required·forbidden과 기존 항목별 판정을 그대로 사용하며 결과를 본 뒤 변경하지 않는다.

실행 도구는 tools/run_review_evaluation.py다. 인자 없이 실행하면 네트워크 없이 계획을 출력하며, --execute-approved를 명시해야 API를 호출한다. 출력 폴더가 이미 있으면 중단하여 재실행으로 원본을 덮거나 유료 호출을 자동 재개하지 않는다. plan.json에 데이터·도구·프롬프트 지시·요청 템플릿의 해시, 실행 순서와 채점 기준을 호출 전에 보관한다.

각 trial에서 두 버전을 번갈아 실행하고 두 번째 trial은 버전 순서를 반대로 한다. corrected와 partial-fix는 동일 버전·trial의 missing-last 응답과 열람한 1단계 힌트를 이전 문맥으로 사용한다. 이전의 유효 응답을 얻지 못하면 해당 종속 사례는 건너뛰고 실패·누락을 기록한다. 따라서 재제출 두 사례의 전체 입력은 버전 간 완전히 동일하지 않다. 나머지 사례는 system instruction을 제외한 입력·응답 스키마가 같다.

초기 공개 평가는 실패 제출의 리뷰 본문과 1단계 힌트를 대상으로 한다. 원본 javac 진단은 허용 근거로 유지하되, 첫 힌트에서 그 수정 토큰을 직접 넣으라고 하면 실패다. 원인 범주만 안내하면 통과, 경계가 애매하면 판단 보류다. 정상 제출은 초기 공개의 해당 없음으로 처리한다. 재제출 비교는 수정 전후 코드·실행 결과를 명시적으로 연결해야 하며, partial-fix의 남은 실패를 해결됐다고 하면 실패다.

실행 일치·인용 유효성·해석 정확성·초기 공개·정상 코드 오경고·재제출 비교를 각각 기록한다. 판단 보류·해당 없음을 통과로 세지 않는다. 채점은 Codex의 원본 응답 검토이며 독립적인 사람의 검수는 아니다. 반복당 결과, 사례별 3회 일관성, 항목별 분모, 토큰·요청 시간과 실패를 함께 보고한다. 중간 결과로 프롬프트나 사례를 바꾸거나 성공할 때까지 호출하지 않는다.

v3 compile-error의 첫 힌트는 세 번 모두 세미콜론이 필요하다고 직접 안내했다. v4는 세 번 모두 실행문의 종결 규칙을 점검하도록 안내했다. 두 버전 모두 evidence에는 허용된 원본 javac 진단이 있으므로, 화면 전체에서 수정 방법을 알아낼 수 없도록 막았다는 의미는 아니다.

v3 partial-fix trial 1은 첫 힌트에서 정확한 범위 0부터 N-1까지를 제시했다. 앞선 단일 평가에서 같은 유형을 판단 보류로 둔 기준을 유지했다. v3 partial-fix trial 1·3은 mixed의 실패를 설명했지만, singleton이 이전 실패에서 통과로 바뀐 변화와 새 분기를 명시적으로 연결하지 않아 비교 기준에 실패했다. v4는 세 번 모두 singleton 해결과 mixed의 남은 실패를 구분했다.

비교 설명의 **위치**는 응답 전체의 비교 통과와 별도로 관찰했다. v3은 evidence에 1/6, 2단계 힌트에 3/6, 비교 누락 2/6이었다. v4는 evidence에 6/6이었다. 특히 corrected의 v3 trial 1·3은 비교가 힌트에만 있으나, 실제 CLI는 통과 시 힌트를 공개하지 않으므로 사용자는 그 비교를 볼 수 없다. 응답 전체의 비교 기준에 통과했다고 이 화면 한계를 숨기지 않는다.

### 해석 범위와 재현

이제는 “고정 8개 사례에서 버전별 3회 반복 평가했고, 컴파일 오류 초기 힌트와 부분 수정 비교에서 v4의 일관된 변화가 관찰됐다”고 기술할 수 있다. 이 결과를 일반적인 모델 정확도·상용 운영 안정성·다른 문제 유형에서의 안정적 개선으로 확대하지 않는다. 단일 배열 합계 문제에 사례가 집중되어 있고, 독립적인 사람의 채점·다른 날짜의 반복·다른 모델 비교는 하지 않았다. 새 네 사례를 본 후에도 프롬프트를 추가 조정하지 않았다.

코드 검증과 응답 재생은 `./gradlew build --rerun-tasks`로 API 없이 수행한다. `python3 tools/run_review_evaluation.py`는 API 없이 새 실행 계획만 출력한다. 실제 호출은 별도 승인 후 `--execute-approved`와 사용하지 않은 출력 폴더를 명시해야 하며, 기존 폴더가 있으면 호출 전에 중단한다. 재현 실행도 유료 API를 다시 호출하므로 이번 승인의 범위에 포함하지 않는다.
