# ADR 0007: 분석·실행 근거로 리뷰와 코드 변경 검증을 확장한다

- Status: Accepted
- Date: 2026-10-14

## Context

현재 제출 workflow는 컴파일·테스트 결과와 제출 코드를 리뷰 입력으로 사용하고, 제출 사본과 소스 SHA-256을 보관한다. 이를 기반으로 정적 분석 결과를 학습 힌트에 연결하고, 이후 저장소 변경의 영향 분석과 CI 검토로 확장하려 한다.

에이전트가 코드에 대한 설명이나 수정안을 제시하더라도, 그 주장을 뒷받침하는 근거와 검증 범위를 확인할 수 있어야 한다. 큰 저장소에서는 변경과 관련된 코드를 선택하는 기준과 분석하지 못한 영역도 필요하다.

이 ADR은 확장 방향과 구현 순서를 결정한다. 아래 기능은 구현 목표이며, 현재 구현 완료를 의미하지 않는다. 실행 판정과 LLM 판단의 분리는 ADR 0002를, 에이전트 품질 평가는 ADR 0005를 따른다.

## Decision

### 정적 분석 근거를 리뷰 입력으로 제공한다

- 정적 분석 결과를 구조화하고 근거 ID, 파일, 소스 위치, 규칙 ID, 분석 도구·버전, 소스 해시를 기록한다.
- 메서드·타입·참조 관계와 컴파일·테스트 결과를 함께 사용해 코드 흐름, 실패 원인과 단계별 힌트를 설명한다.
- 리뷰는 제공된 근거 ID를 인용하며, 존재하지 않는 근거나 다른 소스 버전의 근거를 인용한 응답은 검증 실패로 처리한다.
- 분석·실행으로 확인한 사실과 LLM이 추론한 가설을 구분한다. 정적 분석 경고만으로 오답이나 시간 복잡도를 확정하지 않는다.
- 재제출에서는 이전 결과와 비교해 해결된 문제, 새로 발생한 문제와 남은 문제를 설명한다.

### 저장소 변경의 영향 범위를 단계적으로 분석한다

- 저장소 분석의 입력은 기준 커밋과 변경 커밋으로 고정한다.
- 변경된 메서드·타입, 참조 코드, 관련 테스트와 분석 결과의 차이를 수집하고, 선택 근거와 함께 리뷰 입력으로 제공한다.
- 첫 범위는 Java/Kotlin의 단일 모듈과 직접 참조 관계로 제한한다. 리플렉션·동적 호출 등 추적하지 못한 영역은 미확인 범위로 표시한다.
- 분석 결과 재사용 시 커밋·파일 해시뿐 아니라 분석 도구·설정과 의존성 변경을 확인한다. 관련 입력이 바뀌면 캐시를 무효화한다.
- 컨텍스트 크기 제한으로 제외한 파일이나 분석 범위를 기록한다. 일부 컨텍스트만 사용한 리뷰를 저장소 전체 검증으로 표현하지 않는다.

### 코드 변경을 정해진 검사로 검증한다

- 변경안을 격리된 작업 공간에 적용하고 컴파일·정적 분석·테스트를 실행한 뒤 기준 버전의 결과와 비교한다.
- 검증 결과에 대상 커밋 또는 소스 해시, 실행한 검사와 설정, 실행 결과, 미실행·미확인 항목을 남긴다.
- 필수 검사와 허용 기준은 명시적인 정책으로 정하고, 에이전트가 판정을 변경하지 못하게 한다.
- 결과는 다음 기준으로 구분한다. 필수 검사 실패가 확인되면 실패로 판정하고, 함께 발생한 미확인 항목도 보존한다.

| 결과 | 기준 |
|---|---|
| 통과 | 설정한 필수 검사를 모두 완료하고 허용 기준을 만족함 |
| 실패 | 필수 검사에서 위반이나 실패를 확인함 |
| 미확인 | 확인된 필수 검사 실패는 없으나 검사 누락이나 실행 기반 오류 등으로 판정을 완료하지 못함 |

- 문제의 실행 시간 제한 초과는 기존 제출 판정을 따른다. 검증 도구나 CI 작업 자체의 시간 초과는 미확인 항목으로 기록한다.
- 통과는 해당 검사 범위의 결과이며 코드의 모든 동작이나 운영 적합성을 보장하지 않는다.
- 에이전트가 제안한 테스트에는 예상 결과의 근거가 필요하다. 코딩테스트에서는 작은 입력의 신뢰할 수 있는 기준 풀이 또는 문제 명세가 보장하는 성질을 활용한다.
- 작업 공간 분리와 실행 보안 격리를 구분한다. 외부의 신뢰하지 않는 코드를 실행하기 전에는 파일·네트워크 접근과 자원 사용을 제한하는 실행 환경을 별도로 설계한다.

### CI 검토와 에이전트 품질 평가를 분리한다

- PR 검토 에이전트는 변경 내역과 분석·테스트 결과를 받아 근거를 인용한 보고서를 CI 결과물로 생성한다.
- 빌드와 필수 검사 통과 여부는 검사 정책이 결정한다. 리뷰 API 장애나 응답 검증 실패는 별도 리뷰 상태로 기록한다.
- 기본 CI는 외부 LLM 호출 없이 빌드·테스트와 고정 fixture 검증을 수행한다. 실제 API를 사용하는 검토·평가는 수동 또는 명시적으로 활성화한 workflow로 분리한다.
- PR 코드와 분석 출력은 신뢰하지 않는 입력으로 취급한다. 외부 코드 실행 단계에 API 키나 쓰기 권한을 제공하지 않으며, 에이전트의 기본 권한은 보고서 생성에 필요한 범위로 제한한다.
- 프롬프트·모델·분석기 변경은 버전 관리되는 고정 사례로 평가한다. 근거 인용 유효성, 실행 결과와의 모순, 알려진 문제 탐지, 정상 코드 오경고, 정답 조기 노출, 응답 실패를 추적한다.
- 평가 결과에는 사례별 원본 결과, 집계 분모, 모델·프롬프트·분석기 버전을 남긴다. 요청 시간과 토큰 사용량을 기록하며, 비용을 산출할 경우 적용한 단가와 기준일도 보관한다.
- 학습자의 제출 기록과 에이전트 평가 기록은 분리한다. 의미적 평가에 사람의 판단이나 별도 평가 모델을 사용하면 평가 방식과 한계를 기록한다.

### 제출 단위에서 Git 변경 단위로 확장한다

1. 제출 코드의 정적 분석 결과를 구조화하고, 근거를 인용하는 단계별 힌트와 재제출 비교를 구현한다.
2. 변경 전후 컴파일·분석·테스트 결과를 비교하는 검증 기능을 구현한다.
3. 입력 범위를 Git 변경으로 확장하고 직접 참조 코드·관련 테스트를 선택한다.
4. CI 검토 보고서와 고정 사례 기반 에이전트 회귀 평가를 연결한다.

분석 도구, 실행 격리 기술, 다중 모듈 지원 범위와 품질 회귀 차단 임계값은 각 단계의 요구사항과 측정 결과를 근거로 별도 결정한다.

## Consequences

- 학습 힌트와 저장소 변경 리뷰가 동일한 근거·검증 흐름을 사용할 수 있다.
- 리뷰의 주장을 소스 버전과 검사 결과까지 추적할 수 있지만, 근거 인용이 유효하다는 사실만으로 설명의 정확성이 보장되지는 않는다.
- 저장소 전체를 매번 리뷰 입력에 포함하지 않아도 되지만, 참조 분석의 누락과 컨텍스트 선택 품질을 평가해야 한다.
- 분석 도구·규칙·의존성 변경에 따른 결과 차이와 캐시 무효화를 관리해야 한다.
- 검증 통과 범위와 미확인 범위를 함께 제공해야 하며, 테스트 예상 결과와 평가 사례 자체의 신뢰성도 관리해야 한다.
- 구현 후 포트폴리오에는 실제 지원 범위와 평가 데이터로 확인한 결과만 기술한다. 대규모 저장소 처리 능력이나 품질 개선 수치는 별도 측정 없이 주장하지 않는다.
