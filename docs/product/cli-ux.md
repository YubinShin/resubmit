# CLI UX

## 문서 목적

Re:Submit CLI의 사용자 흐름, 화면에 표시할 정보, 사용자 입력이 필요한 지점과 오류 처리 원칙을 정의한다.

이 문서는 목표 UX를 설명한다. 실제 구현 여부는 README와 코드·테스트를 기준으로 확인한다.

## 목표

- 사용자가 파일과 실행 명령을 관리하기보다 문제 풀이에 집중하게 한다.
- 사용자가 각 단계에서 무엇을 해야 하는지 바로 알 수 있게 한다.
- 컴파일·테스트 결과와 LLM 해석을 구분한다.
- 중단, 외부 API 오류와 잘못된 입력이 학습 기록을 유실시키지 않게 한다.

## UX 원칙

1. CLI가 세션 폴더와 `Solution.java` 템플릿을 생성한다.
2. 한 화면에는 현재 가능한 행동을 4개 이하로 표시한다.
3. 컴파일·테스트 결과를 먼저 보여주고 LLM 리뷰는 별도로 표시한다.
4. 힌트와 개선 풀이는 사용자가 요청할 때만 공개한다.
5. 중단된 세션은 실패 처리하지 않고 저장 후 재개할 수 있게 한다.
6. 기존 파일은 사용자 확인 없이 덮어쓰지 않는다.
7. LLM 오류가 발생해도 실행 결과와 제출 이력은 보존한다.
8. 숙련도 점수보다 제출에서 확인한 관찰 근거를 먼저 보여준다.
9. fixture demo와 실제 코드·LLM 실행을 명확히 구분한다.
10. 구현되지 않은 기능은 동작하는 것처럼 표시하지 않는다.
11. 대화형 터미널에서는 상태 전환마다 같은 화면을 다시 그리고, 비대화형 환경에서는 순차 출력한다.

## 핵심 사용자 흐름

```text
첫 실행
  → 문제 시작
  → 세션 폴더와 Solution.java 생성
  → 사용자 편집
  → Enter로 제출
  → 컴파일·테스트 결과
  → 선택적 힌트
  → 같은 파일 수정
  → 재제출
  → 완료 기록
```

## 초기 진단 흐름

초기 진단은 사용자가 매 단계 프롬프트를 작성하지 않아도 CLI가 정해진 workflow를 진행한다. 사용자는 시작 전에 자기보고에 답하고, 이후에는 각 문제를 풀고 제출하는 데 집중한다.

```text
진단 시작
  → 언어·경험·목표와 유형별 자신감 입력
  → 자기보고 프로필 저장
  → 진단 문제 세트 구성
  → 문제별 제한 시간 안내 및 풀이
  → 제출마다 컴파일·테스트·리뷰
  → 남은 진단 문제 자동 제시
  → 자기보고와 관찰 결과를 구분한 초기 프로필
  → 다음 학습 세션 제안
```

- 자기보고는 사용자가 인식한 수준으로 보관하고, 제출 결과는 관찰 근거로 별도 보관한다. 관찰 결과가 자기보고를 덮어쓰지 않는다.
- 초기 진단은 배열·해시, 탐색, 스택 등 여러 유형을 포함하는 4~6문제 구성을 목표로 한다. 실제 문항과 시간 배분은 진단 세트 정의에서 관리한다.
- 문제별 타이머는 진단 세션의 풀이 시간 측정에 사용한다. 종료·중단 시 경과 시간과 제출 여부를 구분해 기록하며, 제한 시간 종료만으로 오답 판정을 내리지 않는다.
- 제출 뒤 평가와 기록을 마치면 다음 문제를 자동으로 제시한다. 사용자는 언제든 세션을 일시 종료하거나 종료할 수 있어야 한다.
- 최종 프로필은 점수만 제시하지 않고, 각 유형에 대해 자기보고, 관찰 결과, 근거가 된 제출·힌트 사용 여부를 나란히 보여준다.
- 초기 프로필을 근거로 다음 학습 목표와 문제를 제안한다. 추천 근거가 부족하면 확정적인 숙련도 표현 대신 추가 관찰이 필요하다고 표시한다.

예시 요약:

```text
초기 진단 결과

유형       자기보고   관찰   근거
BFS        4 / 5      보통   기본 탐색 통과, 방문 처리 수정 후 통과
스택       2 / 5      확인 중 진단 근거 부족

다음 학습 제안
방문 처리와 최단 경로 문제를 순서대로 연습합니다.
```

초기 진단은 현재 구현 완료 기능이 아니라 후속 workflow 목표다. 현재 CLI 제출 흐름의 fixture 리뷰나 단일 문제 경험을 진단 결과로 표시하지 않는다.

## 세션 작업 공간

CLI가 문제를 시작할 때 세션별 작업 공간을 생성한다.

```text
.resubmit/
└── sessions/
    └── 20261007-001-target-number/
        ├── Problem.md
        └── Solution.java
```

- `.resubmit/`은 Git 추적에서 제외한다.
- `Problem.md`에는 문제 설명, 제출 규약과 공개 예제를 기록한다.
- `Solution.java`에는 정답이 아닌 클래스·메서드 골격만 생성한다.
- 같은 경로에 파일이 있으면 자동으로 덮어쓰지 않는다.

템플릿 예시:

```java
public class Solution {
    public int solution(int[] numbers, int target) {
        // TODO: 구현하세요.
        return 0;
    }
}
```

## 화면별 명세

### 첫 실행

첫 실행에서는 전체 기능을 설명하기보다 예제 문제를 바로 시작할 수 있게 한다.

```text
Re:Submit에 오신 것을 환영합니다.

테스트 결과를 바탕으로 오답 원인을 분석하고,
정답을 바로 보여주지 않는 단계별 힌트를 제공합니다.

[Enter] 예제 문제 시작
[d] 기록된 데모 보기
[q] 종료
```

- fixture demo는 API 키 없이 실행할 수 있어야 한다.
- 실제 실행과 fixture 응답을 화면에 명시한다.

### 문제 시작

```text
Re:Submit — Evidence-based Coding Test Coach
작업 파일을 만들었습니다.
  문제  /workspace/…/target-number-demo/Problem.md
  제출  /workspace/…/target-number-demo/Solution.java

제출 준비

[e] 편집  [Enter] 제출  [q] 종료
>
```

- 제목, 상태, 경로와 가능한 행동을 시각적으로 구분한다.
- 문제와 제출 파일 경로는 세션 생성·재개 직후에만 표시한다.
- 표시하는 파일 경로는 정규화된 절대 경로를 기준으로 하되 터미널 폭을 넘으면 가운데를 `…`로 줄이고 파일명을 보존한다.
- 문제 설명과 제출 규약은 터미널 폭에 맞춰 줄바꿈한다.
- 화면에는 영문 단축키만 표시하고, 기존 한글 키보드 입력도 동일하게 처리한다.
- CLI는 제출을 기다리는 동안 세션을 유지한다.

### 에디터 열기

에디터 선택 우선순위는 다음과 같다.

1. `RESUBMIT_EDITOR`
2. `EDITOR`
3. 파일 절대 경로와 수동 편집 안내

CLI는 선택한 명령을 shell 없이 인자 목록으로 실행하고 `Solution.java` 절대 경로를 마지막 인자로 전달한다. 에디터 프로세스가 종료되면 제출 대기 화면으로 돌아간다. 실행할 수 없거나 0이 아닌 종료 코드로 끝나도 제출 실패로 처리하지 않고, 실패 메시지와 파일 절대 경로를 표시한다. 에디터 환경변수 값과 실행 명령은 JSONL 이력에 저장하지 않는다.

첫 MVP에서는 특정 IDE를 자동 탐지하지 않으며, 백그라운드 GUI 에디터의 저장 완료도 감지하지 않는다. 해당 에디터를 사용할 때는 저장 완료까지 대기하는 인자를 환경변수에 직접 지정해야 한다. 에디터 환경변수가 없더라도 파일 경로를 복사해 열 수 있어야 한다.

### 제출 결과

실행 사실과 해석을 섞지 않는다.

```text
Attempt 1

컴파일      PASS                412 ms
테스트      3 / 5 PASS          184 ms
리뷰        READY               fixture

실패한 테스트
  case-4  expected 5, actual 3
  case-5  expected 2, actual 0

[h] 1단계 힌트
[e] 다시 편집
[q] 저장하고 종료
```

- 정오답과 실행 상태는 `CodeRunner` 결과만 사용한다.
- LLM 리뷰가 정오답을 변경하지 않는다.
- 컴파일 실패는 javac 진단을 근거로 별도의 `컴파일 오류` 리뷰와 단계별 힌트를 제공한다. 테스트 상태는 `NOT_RUN`으로 기록한다.
- 제목만 bold로 표시하고 메타데이터와 경로는 muted, 상태값은 색상과 텍스트를 함께 사용한다.
- 문제·실행 결과·리뷰·명령 영역은 구분선 없이 빈 줄과 들여쓰기로 구분한다.
- 상태 레이블과 값은 실제 터미널 셀 폭으로 정렬하고, 좁은 화면에서는 긴 상세 정보를 다음 줄로 내린다.
- 화면에는 요약을 표시하고 stdout, stderr와 실행 명령은 상세 기록에 남긴다.
- 외부 LLM 리뷰를 기다리는 동안 spinner, provider와 경과 시간을 같은 줄에 갱신한다.
- 화면 전환을 사용하지 않는 환경에서는 `리뷰 요청 중…`을 한 번 출력한다.
- 같은 attempt의 실행·리뷰·힌트 revision은 모두 JSONL에 append하되 `이력 저장됨` 메시지는 attempt당 한 번만 표시한다.

### 힌트

힌트는 자동으로 노출하지 않는다.

```text
힌트 1/3 — 방향만 제시

각 숫자마다 선택지가 몇 개인지 생각해보세요.
현재 상태에서 다음 상태로 이동하는 두 경우를 비교해보세요.

힌트를 확인한 기록이 저장됩니다.

[e] 다시 편집
[h] 다음 힌트
```

힌트 단계:

1. 관련 개념과 확인할 지점
2. 현재 제출 코드의 구체적인 문제
3. 의사코드 또는 개선 방향

완성 풀이 확인은 힌트와 분리한다. 사용자가 풀이를 확인하면 해당 attempt 이후 이력에 `solutionViewed=true`를 기록한다.

### 재제출

이전 attempt와 달라진 실행 사실을 보여준다.

```text
Attempt 2

테스트   3/5 → 5/5
결과     FAILED → PASSED
힌트     1단계 사용
변경     source hash 변경 확인
```

한 번의 통과만으로 일반적인 실력 향상을 주장하지 않는다.

- 리뷰 provider에는 직전 attempt의 실행 결과, 사용자가 실제로 확인한 힌트, 저장된 제출 코드가 참고 정보로 전달된다. 현재 attempt의 컴파일·테스트 결과가 판정의 기준이다.
- 직전 제출 코드가 길면 앞뒤 일부만 리뷰 문맥에 넣고 생략 표시를 한다.
- 이력에는 생성된 리뷰 전체와 model/prompt version을 저장한다. 힌트 열람 단계는 별도 기록해 사용자가 보지 않은 힌트를 열람한 것으로 취급하지 않는다.

### 문제 완료

```text
문제 완료

첫 제출      3/5
최종 제출    5/5
제출 횟수    2
힌트 사용    1단계
관찰 근거    재귀 상태 전이 오류 수정

[n] 다음 문제
[r] 실행 기록 보기
[q] 종료
```

## 오류 상태

### 컴파일 실패

```text
컴파일하지 못했습니다.

Solution.java:8
';' expected

[h] 힌트  [e] 파일 수정  [q] 저장 후 종료
```

- javac 오류 위치와 메시지를 우선 표시한다.
- 테스트는 실행하지 않고, javac 오류와 제출 코드를 바탕으로 컴파일 실패 리뷰를 제공한다.
- 컴파일 실패 리뷰는 컴파일러가 보고한 오류와 현재 제출 코드만 근거로 삼고, 정오답 판정을 만들지 않는다.

### 테스트 실패

- 통과한 테스트 수와 실패한 공개 테스트를 표시한다.
- 숨겨진 테스트의 입력 전체나 정답을 노출하지 않는다.
- 재제출과 힌트 중 다음 행동을 선택할 수 있게 한다.

### 시간 초과

```text
실행이 2초 제한을 초과해 종료됐습니다.
프로세스는 강제로 정리했습니다.

[h] 복잡도 관련 힌트
[e] 다시 편집
```

시간 제한과 프로세스 정리 여부를 함께 표시한다.

### LLM 오류

```text
테스트 결과는 저장됐습니다.
리뷰 API가 응답하지 않아 힌트는 생성하지 못했습니다.

[r] 리뷰 다시 요청
[e] 리뷰 없이 다시 편집
```

- LLM 실패를 제출 실패로 표시하지 않는다.
- 리뷰 재시도 여부는 사용자가 선택한다.

### 잘못된 입력

전체 화면을 다시 출력하지 않고 사용할 수 있는 입력을 짧게 안내한다.

```text
'x'는 사용할 수 없는 명령입니다. 가능한 명령: e, h, q
```

## 종료와 재개

`q`, EOF와 `Ctrl+C`를 고려한다.

```text
중단된 세션
20261007-001-target-number

[r] 이어서 풀기  [n] 새로 시작  [q] 종료
>
```

다음 실행에서 진행 중인 세션을 발견하면 이어서 풀기와 새 문제 시작을 선택하게 한다. 화면에는 영문 단축키만 표시하지만 한글 키보드 입력도 허용한다. 제출하지 않은 편집 상태와 실패한 attempt를 구분한다.

## 명령 체계

화면별 명령:

- `Enter`: 현재 기본 행동 실행
- `e`: 제출 파일 편집
- `h`: 현재 단계의 힌트 확인
- `r`: 실행 또는 세션 기록 확인
- `q`: 저장 후 종료

전역 명령 후보:

- `?`: 현재 가능한 명령 표시
- `status`: 현재 세션 상태 표시
- `quit`: 저장 후 종료

첫 MVP에서는 화면별 명령만 구현하고, 실제 필요가 확인되면 전역 명령을 추가한다.

## 타이머

일반 풀이 화면의 카운트다운 UI는 후속 범위다. 초기 진단에서는 문제별 풀이 시간을 측정하고 만료 시 제출 대기 상태를 종료하는 흐름이 필요하다. 두 기능을 혼동하지 않도록 진단 풀이 시간과 일반 세션 경과 시간을 구분한다. 다음 원본 시각은 저장할 수 있게 데이터 모델을 설계한다.

- `startedAt`
- `firstSubmittedAt`
- `completedAt`
- 진단 문제별 `problemStartedAt`, `deadlineAt`, `submittedAt` 또는 동등한 경과 시간 근거

진단 세션을 재개할 때는 남은 시간을 보존하거나 만료 처리하는 규칙을 명시한다. pause, resume, 힌트 확인 시간 분리와 일반 풀이의 제한 시간 표시는 실제 사용 후 추가한다.

## 접근성과 터미널 호환성

- 색상만으로 PASS와 FAIL을 구분하지 않는다.
- 대화형 터미널에서는 alternate screen을 사용하지 않고 상태 전환 시 현재 화면을 다시 그린다.
- 에디터 프로세스가 종료되면 CLI 화면을 다시 그린다.
- `RESUBMIT_NO_TUI`가 있거나 `TERM=dumb`이면 화면 전환 없이 순차 출력한다.
- 지원하는 터미널에서는 제목에 bold, PASS·FAIL·TIMEOUT에 ANSI 색상을 사용한다.
- `NO_COLOR`가 있거나 `TERM=dumb`이면 ANSI 스타일을 사용하지 않는다.
- 한글 메시지와 javac 원문 오류를 구분한다.
- 터미널 폭은 `/dev/tty`, `COLUMNS`, 기본 80열 순서로 결정한다.
- 출력과 경로는 자동 줄바꿈을 피하도록 감지한 폭보다 한 칸 짧게 표시한다.
- 공백과 한글이 포함된 긴 파일 경로는 가운데를 줄여 파일명을 보존한다.
- 에디터 실행 실패 시 수동 편집에 필요한 전체 절대 경로는 줄이지 않고 출력한다.

## 사용자 화면과 상세 기록의 분리

화면에는 다음 정보만 요약한다.

- compile/test 상태
- 통과한 테스트 수
- 소요 시간
- 리뷰 상태
- 현재 가능한 행동

상세 기록에는 다음을 남긴다.

- session/attempt ID
- 실행 명령과 exit code
- stdout, stderr와 출력 절단 여부
- 테스트별 결과와 duration
- 제출 코드 hash
- review provider, failure type와 evidence
- review의 관련 기술과 생성한 힌트
- hint level과 hintViewed
- review 실패 상태와 오류 메시지
- model/prompt version
- API·schema 오류

개발과 장애 확인을 위한 `--verbose` 옵션은 후속 범위로 둔다.

## 자동 진행과 사용자 확인

자동 처리:

- 세션 폴더와 템플릿 생성
- session/attempt ID 생성
- 컴파일과 테스트
- 결과 저장과 요약
- 다음 힌트 단계 계산
- 진단 workflow에서 평가 완료 후 다음 문제 제시
- 진단 종료 후 근거가 있는 초기 프로필과 학습 제안 생성

사용자 확인 필요:

- 기존 파일 덮어쓰기
- 힌트와 개선 풀이 확인
- 새 문제 이동
- LLM 리뷰 재시도

## MVP 범위

우선 구현:

- 세션 폴더 생성
- `Problem.md`와 `Solution.java` 생성
- 편집 후 Enter로 제출
- 컴파일·테스트 결과 요약
- 저장 후 종료
- 다단계 힌트
- 세션 재개
- 환경변수로 선택한 에디터 실행과 수동 편집 fallback

후속 구현:

- 타이머 UI
- 문제 선택
- 학습 프로필과 추천
- 전역 명령과 `--verbose`
- 자기보고 입력과 4~6문제 초기 진단 workflow
- 자기보고 수준과 제출에서 관찰한 근거를 분리한 프로필
- 진단 결과를 바탕으로 다음 학습 세션 자동 제안
- 유형·문제·선수 관계를 이용하는 선택적 그래프 기반 추천
- 고정 평가 사례를 이용한 agent 품질 회귀 평가

후속 기능의 순서:

1. 컴파일·테스트·리뷰·재제출 이력을 한 문제 workflow에서 안정화한다.
2. 문제 정의와 실행 규약을 분리해 여러 문제를 같은 workflow에서 실행할 수 있게 한다.
3. 자기보고와 시간 제한 풀이를 이용하는 초기 진단을 만들고, 자기보고와 관찰 근거를 분리해 저장한다.
4. 먼저 로컬 저장소와 명시적인 선수 관계를 이용해 다음 문제를 제안한다.
5. 여러 단계 관계 탐색이 실제 추천에 필요해졌을 때 그래프 저장소 adapter와 관리형 Neo4j 연결을 검토한다.

그래프DB는 초기 진단이나 CLI 실행의 필수 조건이 아니다. 도입 여부는 추천에 필요한 관계 질의와 로컬 구현의 한계를 확인한 뒤 결정한다.

## 평가와 이력의 원칙

- 컴파일·테스트 결과는 실행 도구가 만든 결정론적 사실로 저장하고, LLM이 이를 바꾸지 않는다.
- LLM 리뷰에는 입력 근거와 결과를 연결해 기록한다. provider 오류나 구조화 응답 오류는 리뷰 실패로 기록하며 제출 실행 결과를 보존한다.
- 사용자 학습 기록과 agent 평가 실행은 목적과 저장 공간을 분리한다. CI 평가 결과를 사용자 숙련도 이력으로 섞지 않는다.
- 진단 결과는 평가 사례와 관찰 횟수에 한계를 함께 표시한다. 적은 문제 수로 장기적인 실력 향상을 주장하지 않는다.
